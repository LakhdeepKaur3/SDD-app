# Research: Full-Stack Todo App

**Date**: 2026-09-01
**Branch**: `001-fullstack-todo-app`

## Summary

The project constitution fully prescribes the technology stack, leaving no ambiguous choices. All decisions below are either mandated or derived directly from the constitution's constraints. No NEEDS CLARIFICATION items remain.

---

## Decision 1: Frontend Framework

**Decision**: Next.js 14 (App Router) with React 18 and TypeScript

**Rationale**: Mandated by constitution. App Router supports React Server Components and co-located layouts. The single route `/` maps to `frontend/app/page.tsx`.

**Alternatives considered**: Not applicable — mandated.

---

## Decision 2: Styling

**Decision**: Tailwind CSS utility classes only; `globals.css` contains only the three `@tailwind` directives

**Rationale**: Mandated by constitution. No custom theme extension, no separate layout CSS files.

**Alternatives considered**: Not applicable — mandated.

---

## Decision 3: Backend Framework

**Decision**: Node.js 20 + Express 4 + TypeScript

**Rationale**: Mandated by constitution. Express is minimal and aligns with the layered architecture (routes → controllers → services) the constitution requires.

**Alternatives considered**: Not applicable — mandated.

---

## Decision 4: ORM and Database

**Decision**: Prisma 5 ORM + PostgreSQL 15 running in Docker

**Rationale**: Mandated by constitution. Prisma provides type-safe database access. PostgreSQL runs via Docker; credentials stored in environment variables.

**Alternatives considered**: Not applicable — mandated.

---

## Decision 5: API Style

**Decision**: REST with JSON responses; endpoints follow the constitution's convention

| Method | Path | Purpose |
|--------|------|---------|
| GET | /api/todos | Fetch all todos |
| GET | /api/todos/:id | Fetch a single todo |
| POST | /api/todos | Create a todo |
| PUT | /api/todos/:id | Update a todo (toggle completion) |
| DELETE | /api/todos/:id | Delete a todo |

**Rationale**: Mandated by constitution. Responses use standard HTTP status codes for errors.

**Alternatives considered**: Not applicable — mandated.

---

## Decision 6: Todo Data Shape

**Decision**: `{ id: string, text: string, completed: boolean, createdAt: string }`

- `id` — auto-generated by Prisma/PostgreSQL (UUID or auto-increment)
- `text` — plain text, non-empty, no rich formatting
- `completed` — boolean, default `false`
- `createdAt` — ISO 8601 string; used to sort newest-first (`ORDER BY createdAt DESC`)

**Rationale**: Mandated by constitution.

**Alternatives considered**: Not applicable — mandated.

---

## Decision 7: Frontend State Management

**Decision**: React `useState` + `useEffect` hooks; no external state library

**Rationale**: The app has a single page and a flat data structure. Local component state is sufficient. All mutations call the backend API and then re-fetch or update local state to stay consistent.

**Alternatives considered**:
- Redux / Zustand — unnecessary overhead for a single list
- React Query / SWR — viable but not prescribed; plain `fetch` keeps the stack minimal

---

## Decision 8: Loading and Error States

**Decision**: Per-operation boolean flags (`isLoading`, `error`) managed in React state; displayed inline in the UI

**Rationale**: The spec requires loading indicators during API calls and error messages on failure without losing the current list. Local flags per operation satisfy this without a global state manager.

**Implementation pattern**:
1. Set `isLoading = true` before the API call
2. On success, update the todo list in state, set `isLoading = false`
3. On failure, set `error` message, set `isLoading = false`; keep the existing list intact

---

## Decision 9: Todo Ordering

**Decision**: Sort by `createdAt` descending on the backend (`ORDER BY createdAt DESC` in Prisma query)

**Rationale**: Spec requires newest tasks at top. Sorting server-side avoids client-side sort inconsistencies and is consistent across page loads.

**Alternatives considered**: Client-side sort — works but fragile if `createdAt` values are not returned precisely.

---

## Decision 10: Blank Input Validation

**Decision**: Validate on the frontend (trim whitespace, reject empty string) before sending to the API; also validate on the backend and return HTTP 400

**Rationale**: Spec FR-002 requires the system to reject blank or whitespace-only task submissions. Dual validation (client + server) provides fast user feedback and a safe server boundary.

---

## Decision 11: ID Generation

**Decision**: PostgreSQL auto-generates the `id` (via Prisma's `@default(cuid())` or `@default(autoincrement())`); the browser never generates or stores IDs

**Rationale**: Mandated by constitution. IDs are generated by Prisma/database, not the browser.

**Selected**: `cuid()` — URL-safe, collision-resistant, works well for REST resource identifiers.

---

## Decision 12: Environment Configuration

**Decision**: Backend reads `DATABASE_URL` from a `.env` file; Docker Compose sets the PostgreSQL credentials; the frontend reads the backend base URL from `NEXT_PUBLIC_API_URL`

**Rationale**: Mandated by constitution. Credentials must not be hardcoded.

---

## Resolved Clarifications

No NEEDS CLARIFICATION items were raised in the specification. All scope decisions (single shared list, no auth, no pagination, no real-time sync, no rich text) were documented as assumptions in the spec and are accepted as-is.
